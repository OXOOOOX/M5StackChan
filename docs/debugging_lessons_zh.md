复核日期：2026-09-03。本文将症状、工具证据、用户实机反馈和后续限制放在一起，便于下一次从已知状态继续。原始聊天不随仓库上传。

## 先认清当前状态

- **曾经跑通**：UIFlow2 监听/触摸退出；VM_EN 后的小幅运动；早期遥控动作；更换舵机后的双 ID 通信、Jog、中心校准。

代码可以作为开发内容上传；当前 v0.2/v0.3 原型不应标为已实机验收的稳定发布。

## 1. 先固定环境和源码来源

用户选 MicroPython 的核心原因是高频修改时不想反复完整编译烧录。对应工作流是先准备运行环境，日常整体运行 Python，再分层验证接口；这不承诺未来 C++ 迁移无需重写。（P0:L51–110）

两份历史 bin 实际是 ESP-IDF 主固件和遥控固件，不是 UIFlow2。当前文件元数据分别为 `stack-chan 1.2.6 / IDF v5.5.4` 和 `StackChan-RemoteControl-ESPNow f8d61a2-dirty / IDF v5.4.2-dirty`。固定源码主固件版本是 1.2.4，不能说“下载固件与开源源码完全一致”。元数据、哈希和来源边界见[固件清单](firmware_inventory.md)。（E1:L91–125、L241；本次字节复核）

早期脚本使用旧 `m5stack` API，用户明确收到 `ImportError: no module named 'm5stack'`。改为 UIFlow2 的 `M5`、`M5.begin()`、`Widgets` 后，用户确认 monitor 成功。这是已确认的 API 纠错；不能把 UIFlow1/2、普通 MicroPython 和 ESP-IDF 示例混用。（E3:L204–342）

## 2. 云端控制：入口、链路和猜测分开

EzData 页面没有历史助手所说的 Devices 配对按钮，后来改从 Data 分组/Token 路径继续。设备停在 Pair 页并不直接证明云端命令不可达：用户随后给出 `Received Cmd: 107`、`SERVO.X.ANGLE` 日志，并确认一个轴动了。只证明当次下行和至少一轴动作，未验证双轴全部功能。（E2:L387–474）

当时还有几项未闭环的解释：

| 历史解释 | 实际证据边界 |
| --- | --- |
| 网页整数被 `is<float>()` 拒绝，必须填 20.0 | 是助手根据源码提出的假设，没有原始 JSON 与类型对照实验 |
| 每次启动新增字段且服务端不去重 | 用户确实看见重复字段，但没有数据 ID/服务端行为对照，也没有去重修复验收 |
| UART DEVICE 错误一定是 miniterm 占用 | 有打开终端记录，但没有关闭后重连成功的对照 |
| 浏览器自动化失败一定是安装包 bug | 工具多次报 app-server 启动路径错误；重启/重装未解决，确切原因仍未知 |

经验：截图里的真实页面优先于凭记忆描述的按钮；云端消息、本地 USB 串口和浏览器自动化是三条链路。重复重启而报错不变时，应保留证据并换排查方向。（E2:L121–352、L459–536）

## 3. 黑屏与触摸误触：先做最小 UI

早期整体脚本黑屏，助手猜过 UART、LVGL、内存、阻塞。后来 UI-only 和 UART 初始化各自成功，无法把所有黑屏归成一个已证实根因。（E3:L189、L363、L815、L845）

触摸回归则有清楚的证据链：用户提供 `getCount()=0`，但坐标仍为 `225,188`；历史改动删掉有效按压判断，只看坐标，随后启动立即退出。恢复按压状态与单次触发后成功；新测试 UI 再复用该逻辑并加启动隔离，也成功。（E3:L501–554、L772–815）

可复用规则：

- 松手后残留坐标不代表正在按屏幕。
- 触摸状态、按钮命中、一次按压一次动作、释放后复位要分别处理。
- 防误触必须在新脚本中继续保留，不能每次只复制绘图代码。
- 点击区域按实际按钮适度扩展；用户明确反对扩大成整半屏。（E4:L659–681）

文件尾 `try: main()` 缺完整处理块曾导致 SyntaxError，整体粘贴后恢复。另一次 UIFlow 报错行号与本地空行计数不同，缩短 Widgets 调用后进入下一阶段；不能据此宣称三元表达式、空字符串或长行在 MicroPython 中一律不合法。（E4:L659–681；L2:L84–148）

## 4. 无线排错：先长度，再字段，再 ID

`waiting` 或 `ign` 计数增长不等于无线完全断开。早期增加 `rx / ignored / length` 诊断后可用，但没有当次具体 ID 日志，不宜把首次 waiting 的根因直接定为 ID 错误。（E3:L413–435）

后期出现 `ignored id 42 need id 1`，助手先把 42 当成真实设备目标并加自动配对，后来又见 28 字节包以 `0x2A` 开头。若先对长包做 `packet[:8]` 解码，就可能把封装字节误认成 ID 或角度。实际出现过 yaw `-2500/-7900/-30000`。（L1:L170–174、L393、L633、L701–705）

最终接收端改为：

1. 严格 `len == 8`。
2. 按 `<BhhhB` 解码。
3. 校验 yaw `-1280..1280`、pitch `0..900`、speed `0..1000`。
4. 再核目标 ID；默认不自动配对。
5. 非法包丢弃，不用 clamp 把脏数据变成合法极限动作。

后续有“现在可以遥控了”的用户反馈，证明早期遥控动作曾跑通，不能忽略；这不是全部异常路径验收，而且发生在后续连续旋转事故之前。（L1:L748–787）

28 字节载荷来源未在聊天中逐包确认。远端调试文档将问题关联高层组件封装，并改为原生 `esp_now_send`；不能把全部长包断言为第三方干扰。发送端和接收端都要记录最终 y/p、长度与原始 bytes。（L1:L778–782；远端 `2ce2b47` 的调试说明）

固定官方源码历史上判断 `size() >= 8`；严格等长与范围过滤是本地改进，不应写成官方已经实现的约束。（L3:L36）

用户曾把仍允许长包、关闭异常保护的旧脚本贴回 UIFlow。**本地文件已改不等于设备运行版本已更新**：完整复制文件、输出版本/校验值，再重测。（L1:L728–732）

## 5. UI、UART、应答和运动是四个验收点

历史反馈依次有 `UART initialized`、数字正常跳动、没有卡死，但用户后来明确说舵机仍不动。UI 正常和串口写入正常都不能替代真实动作反馈。（E3:L845–997）

字节序也必须分层：ESP-NOW 控制字段小端；固定官方 SCSCL 的 `End=1`，16 位位置/时间/速度高字节在前。修正早期写反的字节序后，电机仍没动，所以它是协议修复，不是整个故障的唯一根因。（E3:L962–997）

用户提供 `C0 C0 00` 后，继续查官方供电初始化才找到 PY32 VM_EN。固定源码使用 I2C `0x6F`、SDA12/SCL11、PY32 API pin0；UART1 TX6/RX7、1 Mbaud。历史曾把文档 IO 名称误解为代码 pin1，源码的 `digitalWrite(0, enabled)` 才给出正确依据。（E3:L1030–1089）

补齐电源使能后，用户转录了：

```text
0x41
6 FF FF 01 02 00 FB
6 FF FF 01 02 00 FC
```

第一条按实际写出的 ID1 校验不对，不能悄悄改成 ID2；第二条是有效 ID1 状态包。用户后来只确认“小幅动了”，不能扩写成两台都通过 ping 或完整遥控验收。（E3:L1117、L1139）

具体流程见[供电记录](servo_power_debug.md)。后续独立诊断加入帧边界/checksum，比原型严格，但仍未强制 Ping LENGTH=2 或处理非零 error。生产化时必须继续补齐。

## 6. 连续旋转：把失败方案留作经验

用户曾提供 `YAW_ZERO=510 / PITCH_ZERO=610`。它是当时本机校准；机械 raw 零点、Home 姿态和摇杆中位是三个独立概念，不能用一个变量互相代替。也不能把官方 460/620 当所有设备的正确机械中心。（L1:L942、L1000–1022、L1079）

曾尝试把失联回中设为 700 ms，后来用户反馈抬头幅度小、用力回平面，又调回 3 秒并改映射。回中策略需结合发送端是周期发包还是变化才发包；“松杆”“真正断联”“Stop”要有明确区分。（L1:L305、L388、L787–824）

持续 yaw 的实际顺序是：环形角度 → 速度积分 → 前瞻目标 → 取消前瞻 → raw 增量。用户依次反馈跨界失败、慢且断续、回拉，最终异响并在 calibration 里 `no servo`。（L1:L1074–1389）

这里的工程教训是：`%1024` 或最短角差只约束软件数字；没有确认舵机工作模式、0/1023 边界与机械路径前，提高速度不能证明方案正确。原舵机是否机械损坏、保护、接线问题或拖死总线，历史没有拆检证据，不能编造最终根因。

当前自包含脚本还保留 `2048 raw/s`、40 ms 增量方案。应先修复并逐项验收，不能仅因代码存在或编译通过就标“已完成”。

## 7. 更换舵机：先 ID，再 Jog，再中心

后续日志中同时存在 `PY32 post-write read failed: 259`、I2C 扫描含 `0x6F`，以及 ID1 有效应答和底座可动。单条写后读失败不能直接证明 VM_EN 没打开；也不能笼统忽略所有 I2C 错误。把版本读取、写入、读回、UART 应答分别记录。（L2:L148–202）

最有力的恢复证据是：

1. 新 pitch 默认 ID1，扫描只有逻辑 ID1。
2. 断电，断开底座，只接待修改 pitch。
3. 专用脚本扫描、两次确认 Set2，将 EEPROM ID 改为 2。
4. 断电接回两台，用户贴出 ID1/ID2 都有正确应答。
5. 用户确认可 Jog，最后确认 calibration 成功。（L2:L226–299、L466）

```text
ID1: FF FF 01 02 00 FC
ID2: FF FF 02 02 00 FB
```

物理接口不分配 ID，扫描 `[1]` 也不证明总线上只有一个物理舵机。切勿同时连接两个 ID1 后执行改 ID。操作指南见[更换舵机记录](servo_replacement_debug_zh.md)。

Jog 曾只动作首个发现的 ID，容易误认双轴都测过；后改 Jog1/Jog2 分轴 ±18 raw 并关扭矩。校准仍失败时，对比独立诊断的启动路径，补了等待/重试/分项日志后最终成功。但最后没有完整成功日志，无法证明某一个延时就是唯一修复原因。（L2:L272–299、L340–466）

## 9. 构建与 Git 发布：逐层确认结果

历史真实踩坑及可复用处理：

- **读首个实际编译错误**：缺 sdkconfig.defaults/分区文件、I2C 类型冲突、不存在的 Axp192、缺 stdint/stdbool、未启用 LVGL 字体，不能只盯末尾 Ninja 失败。（L3:L287–467；L4:L210–224）
- **defaults 不覆盖已有 sdkconfig**：实际 app 为 `0x118970`，factory 只有 `0x100000`。核对生效配置后改 8MB flash/3MB factory，重新生成配置才构建成功。（L3:L473–509）
- **不要默认 fullclean**：set-target 引发清理，失败残留目录又被 IDF 拒绝；确认目标已有 esp32s3 后使用 reconfigure/build。必要时只处理明确文件。本项目禁止批量删除。（L3:L325–352）
- **构建成功 ≠ 屏幕正常 ≠ 摇杆正常 ≠ 接收动作正常**：当时编译成功后依然黑屏，修屏后仍无摇杆输入，必须分阶段验收。
- **补丁要从已知基线生成**：手改 hunk 曾损坏 patch；PowerShell 默认重定向曾写成 UTF-16。用明确 UTF-8 文本/二进制安全输出方式保存，再做干净基线的 `git apply --check`；reverse check 只证明和现有工作树对应，不等于干净构建可复现。（L3:L109、L399–414；L4:L378）
- **父仓库不携带子模块未提交修改**：要发布可获取的子模块 commit，或完整且可验证的 patch；同时确认正在改正确的仓库。（L3:L1102–1174；L4:L69、L344–368）
- **网络失败与内容冲突分开**：HTTPS 443 超时、TLS、SSH host key/publickey、fetch first、README/patch 冲突是不同层次。先 fetch 确认实际 refs，再解决真实冲突，不能用 force push 代替诊断。（E4:L979–1086；L3:L1199–1396）
- **建分支不等于上传新提交**：E4 的 connector 已把远端同名分支建在初始提交，但新提交 HTTPS push 失败，最终聊天摘要却遗漏了远端建分支成功。必须看当前远端 SHA，而非只看历史结尾。（E4:L1036–1039）
- **发布的 bin 要与源码对应**：曾把旧构建当新输出，又发生 patch 已推但 bin 漏发。核对提交、配置、构建时间、SHA256、输出文件名和刷写偏移；文件名中的版本后缀不是刷写地址。（L3:L1287–1312；L4:L428–533）
- **公开前清洗个人内容**：原始聊天、Token、Wi-Fi 配置、MAC 和本机路径不进入经验文档；识别具体生成物后再忽略，不能凭“pipeline”之类词判断都可删。（L4:L447–587）

本次远端现状以[上传与冲突报告](github_upload_review.md)为准，不沿用历史 push 成败判断。

| 当前 pitch | 中心350、死区100，输入450产生约16.36°目标 | 按实际摇杆中位和装配校准 |
| 校准/内嵌/模块版本 | 510/610 与 460/620 并存，编辑 lib 不影响内嵌脚本 | 明确唯一维护入口，避免文档/代码漂移 |
