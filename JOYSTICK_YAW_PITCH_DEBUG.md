# Unit Joystick2 yaw/pitch Debug Notes

## Problem

StackChan receiver sometimes reports abnormal yaw/Y values from the StickS3 remote, for example:

```text
-2500
-7900
-30000
```

The expected control protocol range is:

```text
yaw:   -1280 .. 1280
pitch: 0 .. 900
speed: 0 .. 1000
```

The red dot on the remote Running screen moves normally, so Unit Joystick2 raw X/Y reading and screen coordinate display are likely working. The main suspect is the value path before ESP-NOW transmission.

## Hardware Reference

Unit Joystick2 reports 16-bit X/Y ADC values over I2C:

```text
I2C address: 0x63
X raw:       0 .. 65535
Y raw:       0 .. 65535
Center:      about 32768
```

For this remote, the joystick input should use the full `0..65535` range for proportional mapping. Input values should not be clipped to a narrower range unless a real calibration system is added.

Reference: https://docs.m5stack.com/en/unit/Unit-JoyStick2

## Original StackChan Remote Mapping

Before adapting the firmware to Unit Joystick2, the original StackChan remote used a different joystick with measured ranges similar to:

```c
#define DEAD_ZONE (300)
#define X_CENTER  (2180)
#define Y_CENTER  (1960)
#define X_MIN     (630)
#define X_MAX     (3730)
#define Y_MIN     (310)
#define Y_MAX     (3460)
```

It then mapped joystick values to the StackChan ESP-NOW protocol:

```c
yaw_angle   = (int16_t)map(joyX, X_MIN, X_MAX, 1280, -1280);
pitch_angle = (int16_t)map(joyY, Y_MIN, Y_MAX, 0, 900);
```

For Unit Joystick2, the equivalent raw range is:

```c
#define JOYSTICK_X_CENTER       32768
#define JOYSTICK_Y_CENTER       32768
#define JOYSTICK_X_MIN          0
#define JOYSTICK_X_MAX          65535
#define JOYSTICK_Y_MIN          0
#define JOYSTICK_Y_MAX          65535
#define JOYSTICK_DEAD_ZONE      3500
```

## Current Fix

Files changed:

```text
StackChan-official/remote/code/main/esp_now/esp_now_init.c
StackChan-official/remote/code/main/esp_now/esp_now_init.h
StackChan-official/remote/code/main/joystick/joystick_handle.c
StackChan-official/remote/code/main/ui/ui_running_screen.c
StackChan-official/remote/code/main/ui/ui_running_screen.h
```

The remote now uses compatibility-mode mapping: keep full-range Unit Joystick2 input, then emit the peer protocol values:

```text
Unit Joystick2 raw 0..65535
        -> proportional yaw/pitch mapping
        -> final protocol range guard
        -> complete ESP-NOW packet
```

The final protocol values are generated by explicit input and output steps:

```c
effective_joy_x = apply_deadzone_u16(effective_joy_x, X_CENTER, DEAD_ZONE);
effective_joy_y = apply_deadzone_u16(effective_joy_y, Y_CENTER, DEAD_ZONE);

effective_joy_x = clamp_u16(effective_joy_x, X_MIN, X_MAX);
effective_joy_y = clamp_u16(effective_joy_y, Y_MIN, Y_MAX);

yaw_angle =
    map_axis_u16_to_i16(effective_joy_x, X_MIN, X_MAX, REMOTE_PROTOCOL_YAW_MAX, REMOTE_PROTOCOL_YAW_MIN);
pitch_angle =
    map_axis_u16_to_i16(effective_joy_y, Y_MIN, Y_MAX, REMOTE_PROTOCOL_PITCH_MIN, REMOTE_PROTOCOL_PITCH_MAX);
```

The mapper performs intermediate math with `int32_t` and clamps the final `int16_t` result to the protocol range. It also handles reversed output ranges, which is required for yaw because `X_MIN..X_MAX` maps to `1280..-1280`.

This means the outer joystick travel is not converted into a dead zone. The raw clamp is `0..65535`, so normal Unit Joystick2 full-range input is still preserved.

The packet is fully populated before any send decision:

```c
pkt[0] = joystick_data->id;
memcpy(&pkt[1], &yaw_angle, sizeof(int16_t));
memcpy(&pkt[3], &pitch_angle, sizeof(int16_t));
memcpy(&pkt[5], &speed_val, sizeof(int16_t));
pkt[7] = joystick_data->btnB_status;
```

This avoids sending an incomplete or stale packet when only the B button state changes.

## Raw ESP-NOW Compatibility

The remote originally used Espressif's higher-level `espnow_send(ESPNOW_DATA_TYPE_DATA, ...)` component API. That API is compatible with the StackChan C++ receiver that uses the same component, but a MicroPython/UIFlow2 `espnow.recv()` receiver can see the component-framed payload instead of the intended 8-byte control payload. In testing this appeared as packets such as:

```text
len 28: 2A 08 10 B0 ...
```

For MicroPython/UIFlow2 compatibility, the remote now uses native ESP-IDF ESP-NOW:

```c
esp_now_send(s_broadcast_addr, pkt, len);
```

The transmitted payload should now be exactly the 8-byte protocol packet:

```text
[target-id][yaw int16 LE][pitch int16 LE][speed int16 LE][laser uint8]
```

## Added On-screen Debug

The Running screen now displays the actual yaw/pitch values about to be sent:

```text
y:<yaw_angle> p:<pitch_angle>
```

Use this to compare:

```text
Remote screen send y/p
StackChan receiver y/p
```

Interpretation:

```text
Remote abnormal, receiver abnormal -> remote mapping/output issue
Remote normal, receiver abnormal   -> receiver parsing or protocol interpretation issue
Remote normal, receiver normal     -> fix is likely valid
```

## Test Checklist

1. Enter the remote Running screen.
2. Move the joystick slowly to all four edges.
3. Confirm the displayed values stay in range:

```text
yaw:   -1280 .. 1280
pitch: 0 .. 900
```

4. Compare the remote `send y/p` display with StackChan receiver logs.
5. Press BtnB while the joystick is still and confirm the receiver does not get abnormal yaw/pitch values.
6. Let the joystick return to center and confirm the dead zone produces stable center values.

## Expected Result

The remote should only transmit complete ESP-NOW packets whose yaw/pitch fields follow the StackChan protocol range. The joystick should still use the full Unit Joystick2 hardware range proportionally, without turning the outer travel into an artificial dead zone.

## Receiver-side Guard

If the remote screen shows normal `y/p` values but StackChan receiver logs an out-of-range value, the problem is no longer the remote mapping display path. The receiver now accepts only exact 8-byte remote packets, logs the first 8 received bytes, and ignores packets outside the protocol range before calling `moveWithSpeed()`:

```text
ignore remote packet with invalid size: ...
raw: <id> <yaw_lo> <yaw_hi> <pitch_lo> <pitch_hi> <speed_lo> <speed_hi> <laser>
ignore invalid remote packet, yaw: ..., pitch: ..., speed: ...
```

This prevents invalid ESP-NOW broadcasts or malformed packets from moving the servos while debugging continues.
